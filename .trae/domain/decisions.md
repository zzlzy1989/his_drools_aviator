## 架构决策详情

### D001: 双引擎架构
**问题**: 为什么同时使用 Drools 和 Aviator？
**选择**: Drools 负责规则匹配和流程控制，Aviator 负责表达式计算
**理由**:
- Drools 擅长复杂业务规则推理（if-then-else、规则优先级、冲突解决）
- Aviator 擅长数学表达式解析和动态公式计算（支持自定义函数）
- 职责分离：规则逻辑与计算逻辑解耦，便于维护
- 性能优化：各自在擅长领域达到最优性能
**替代方案**: A — 仅用 Drools（❌ 表达式编写复杂）；B — 仅用 Aviator（❌ 缺乏规则推理能力）

---

### D002: Skill/Agent 插件化架构
**问题**: 如何支持不同类型的规则处理？
**选择**: SPI 机制 + Spring 自动装配实现插件化
**理由**:
- 新增规则类型只需实现接口，无需修改核心代码
- 支持运行时动态加载/卸载 Skill
- 便于单元测试和集成测试
- 符合开闭原则（对扩展开放，对修改关闭）
**核心接口**:
```java
public interface RuleSkill {
    String getSkillType();
    boolean supports(RuleContext context);
    ExecutionResult execute(RuleContext context);
}
```

---

### D003: 双层缓存架构
**问题**: 如何平衡性能和数据一致性？
**选择**: Caffeine L1（本地高速）+ Redis L2（分布式共享）
**理由**:
- Caffeine：纳秒级访问，适合热点数据（编译后的 Expression、KieSession）
- Redis：跨实例共享，适合规则配置、字典数据
- L1 → L2 → DB 三级降级，保证可用性
- Cache Aside 模式：先更新 DB，再删除缓存

---

### D004: Nacos 配置中心
**问题**: 动态规则参数如何管理？
**选择**: Nacos 统一配置 + @RefreshScope 动态刷新
**理由**:
- 支持配置变更实时生效（无需重启）
- 多环境隔离（dev/test/prod 命名空间）
- 配置版本管理和回滚能力
- 与 Spring Cloud 原生集成
**典型配置项**:
- `his.rule.drools.max-rules`: 单次最大规则数
- `his.rule.aviator.cache-size`: 表达式缓存大小
- `his.settlement.precision`: 金额计算精度

---

### D005: API 前缀统一 /api/v1/
**问题**: URL 路由风格
**选择**: 所有 API 以 `/api/v1/` 为前缀
**理由**:
- 版本化管理，未来升级不破坏现有客户端
- Nginx 反向代理时统一转发规则
- 前端 axios baseURL 一处配置
- 符合 RESTful 最佳实践

---

### D006: 统一响应格式
**问题**: API 响应如何规范化？
**选择**: Result<T> 包装成功/失败，PageResult<T> 处理分页
**理由**:
- 前端统一处理，减少重复代码
- 错误码标准化，便于问题定位
- 支持国际化错误消息
- Swagger 文档自动生成

---

### D007: 全局异常处理器
**问题**: 异常如何统一处理？
**选择**: @RestControllerAdvice + ErrorCode 枚举
**理由**:
- 避免每个 Controller 写 try-catch
- 异常分类清晰（业务异常 / 系统异常 / 参数校验异常）
- 错误码可追溯，便于运维监控
- 敏感信息不泄露给前端

---

### D008: BigDecimal 强制使用
**问题**: 金额计算精度如何保障？
**选择**: 所有金额字段使用 BigDecimal，禁止 double/float
**理由**:
- 浮点数精度丢失问题（0.1 + 0.2 ≠ 0.3）
- 医保结算涉及金钱，精度要求极高
- 提供 BigDecimal 工具类封装常用操作
- 数据库 DECIMAL 类型映射

## 数据模型决策详情

### D009: 规则定义与实例分离
**问题**: 规则如何建模？
**选择**: rule_definition（模板）+ rule_instance（运行时实例）
**理由**:
- 定义层：规则模板、条件、动作的元数据
- 实例层：绑定具体患者、就诊、费用数据
- 支持规则复用（同一模板生成多个实例）
- 版本管理方便（定义变更不影响已运行的实例）

---

### D010: Aviator 公式版本管理
**问题**: 公式变更如何追踪？
**选择**: aviator_formula 主表 + version_history 子表
**理由**:
- 公式可能随医保政策调整而变化
- 历史版本可追溯（审计要求）
- 支持灰度发布（新旧版本并存）
- 回滚机制简单（切换 version 即可）

---

### D011: 结算结果一对多关系
**问题**: 结算结果与费用明细关系？
**选择**: settlement_result 1:N settlement_detail
**理由**:
- 一次结算包含多条费用明细（药品/检查/治疗等）
- 明细级别可展示每项的自付/统筹/补助金额
- 支持明细级别的规则命中记录
- 便于对账和纠纷处理

---

### D012: MySQL utf8mb4 强制要求
**问题**: 数据库字符集选择
**选择**: utf8mb4（非 utf8）
**理由**:
- utf8 只支持 3 字节字符（不含 emoji）
- utf8mb4 支持 4 字节完整 Unicode
- 医疗场景可能涉及特殊符号或 emoji 备注
- MySQL 8.0 默认即为 utf8mb4

---

### D013: 审计日志独立表
**问题**: 操作日志如何存储？
**选择**: audit_log 独立表（非 JSONField）
**理由**:
- 可独立查询和索引日志
- 支持日志保留策略（定期归档）
- 符合医疗信息系统审计要求
- JSONField 无法建立索引和高效查询

---

### D014: LocalDateTime 统一时间
**问题**: 时间字段类型选择
**选择**: Java LocalDateTime + Jackson 序列化为 ISO-8601 格式
**理由**:
- 避免 java.util.Date 的线程安全问题
- 不涉及时区转换（国内系统统一北京时间）
- Jackson 自动序列化/反序列化
- 前端 JavaScript Date 对象直接兼容

## 集成方案决策详情

### D015: KieBase 按业务域分组
**问题**: Drools 规则如何组织？
**选择**: 按 reimbursement/settlement/validation 等业务域分组 KieBase
**理由**:
- 不同域规则相互隔离，避免冲突
- 可独立加载/卸载某个域的规则
- 规则数量可控，提升匹配性能
- 便于权限控制（不同角色可见不同域）

---

### D016: Aviator 表达式池化
**问题**: 高频表达式如何优化性能？
**选择**: Caffeine 缓存编译后的 Expression + 自定义函数注册
**理由**:
- 编译是 CPU 密集型操作，缓存后性能提升 10x+
- 自定义函数扩展 Aviator 能力（如医保政策函数）
- 对象池避免频繁创建销毁
- 支持 EL 表达式语法迁移

---

### D017: 外部 MySQL 策略
**问题**: Docker 部署中数据库如何处理？
**选择**: 禁止容器内 MySQL，使用宿主机已有实例
**理由**:
- 宿主机已有 MySQL 8.0+，无需重复安装
- 数据持久化更有保障（不受容器生命周期影响）
- 备份恢复流程统一
- 降低资源占用

---

### D018: 规则热更新
**问题**: 规则变更如何生效？
**选择**: 基于 Nacos 配置变更事件触发规则重新加载
**理由**:
- 无需重启服务即可生效规则变更
- 支持灰度发布（部分实例先更新）
- 变更可追溯（Nacos 配置历史）
- 减少维护窗口时间

## 业务决策详情

### D019: 分步结算策略
**问题**: 医保结算计算顺序如何设计？
**选择**: 先自费 → 再医保报销 → 最后补充保险
**理由**:
- 符合医保政策规定的计算顺序
- 每步可独立验证和调整
- 便于向患者解释费用构成
- 支持多险种叠加场景

---

### D020: 7 步流程 + 3 个阻塞节点
**问题**: 工作流程如何平衡效率和质量？
**选择**: Step 2(规划)、Step 4(审查)、Step 5(公式验证) 为阻塞节点
**理由**:
- 阻塞节点确保方向正确后再投入大量编码工作
- 公式验证额外阻塞：金额计算错误后果严重
- 非阻塞步骤允许 AI 自主推进（提升效率）
- Bug 修复只保留 Step 4 一个阻塞点
