## 一、执行摘要

### 1.1 背景

随着 AI 编码助手（如 Trae、Cursor、Windsurf 等）在研发团队的普及，我们面临以下挑战：

| 挑战 | 影响 |
|------|------|
| **编码风格不一致** | 不同开发者使用 AI 生成的代码风格差异大，增加维护成本 |
| **知识无法积累** | AI 每次会话从零开始，项目经验无法跨会话持久化 |
| **安全规范难落地** | 依赖开发者"自觉"遵守规范，缺乏硬性约束机制 |
| **新人上手慢** | 业务知识分散在代码和文档中，缺乏结构化知识库 |

### 1.2 解决方案

**Harness 工程体系** 是一套标准化的 AI 辅助开发框架，通过在项目根目录建立 `.trae/` 配置目录，实现：

- ✅ **编码一致性**: 规则驱动，输出稳定一致
- ✅ **知识持久化**: 跨会话积累项目经验和业务知识
- ✅ **安全硬约束**: Hook 拦截机制，防止危险操作
- ✅ **新人快速上手**: 结构化知识库，读文档即可理解业务

### 1.3 核心价值

| 维度 | 传统模式 | Harness 模式 | 提升幅度 |
|------|---------|-------------|---------|
| 代码规范遵循率 | ~60% | ~95% | **+35%** |
| 新人上手时间 | 2-3 周 | 3-5 天 | **缩短 70%** |
| 安全事故发生率 | 中等 | 极低 | **降低 80%** |
| 知识复用率 | <20% | >80% | **提升 4 倍** |

## 二、工程概述

### 2.1 什么是 Harness 工程？

Harness 是一个 **AI Agent 工程框架**，通过结构化的规范、命令、钩子和记忆系统，确保 AI 辅助开发过程中的输出质量和一致性。

**核心理念**: 从 Vibe Coding（经验驱动）到 Harness 工程（系统约束）

### 2.2 目录结构

```
项目根目录/
└── .trae/                    # Harness 工程配置
    ├── agent.md              # AI 行为规范（身份/约束/流程）
    ├── MEMORY.md             # 项目事实知识（技术栈/目录/API）
    ├── settings.local.json   # 权限配置 + 计划管理设置
    │
    ├── rules/                # 编码规范（按领域模块化）
    │   ├── workflow.md       # 7 步强制工作流程
    │   ├── code-style.md     # 编码规范
    │   ├── security.md       # 安全检查
    │   ├── testing.md        # 测试规范
    │   └── ...               # 其他规范文件
    │
    ├── commands/             # 自定义快捷命令
    │   ├── health-check.md   # 环境检查
    │   ├── review.md         # 代码审查
    │   └── ...               # 其他命令
    │
    ├── hooks/                # 事件驱动拦截脚本
    │   ├── pre-task-start.sh     # 任务开始前检查
    │   ├── post-task-complete.sh # 任务完成后处理
    │   └── ...                   # 其他钩子
    │
    ├── domain/               # 业务知识库
    │   ├── glossary.md       # 术语表
    │   ├── rules.md          # 业务规则
    │   └── decisions.md      # 决策记录
    │
    └── workflow-plans/       # 计划生成与跟踪系统
        ├── active/           # 活跃计划
        ├── completed/        # 已完成计划
        └── archived/         # 已归档计划
```

### 2.3 适用场景

| 场景 | 说明 |
|------|------|
| **新项目启动** | 快速建立标准化开发流程 |
| **老项目改造** | 渐进式引入规范，不影响现有开发 |
| **团队协作** | 统一编码风格和业务理解 |
| **知识传承** | 新人快速上手，减少培训成本 |
| **安全合规** | 硬性拦截危险操作，降低安全风险 |

### 3.2 核心功能模块

#### 3.2.1 规范层 (rules/)

| 规范文件 | 功能说明 | 适用场景 |
|---------|---------|---------|
| `workflow.md` | 7 步强制工作流程 + 3 阻塞节点 | 所有开发任务 |
| `code-style.md` | Java/Spring/Drools/Aviator 编码规范 | 编写代码 |
| `security.md` | SQL 注入/XSS/表达式注入防护 | 处理用户输入 |
| `testing.md` | JUnit5/MockMvc/DRL 规则测试 | 编写测试 |
| `api-design.md` | REST API 设计规范 | 设计接口 |
| `database.md` | MySQL 表结构/查询优化/索引规范 | 数据库操作 |
| `error-handling.md` | ErrorCode 体系/异常层级/日志规范 | 错误处理 |
| `docker-deploy.md` | Docker 多阶段构建/JVM 优化 | 部署配置 |
| `performance.md` | Caffeine 缓存/KieBase 分组/并发控制 | 性能优化 |
| `documentation.md` | DRL 规则/Aviator 公式注释规范 | 编写文档 |
| `git-commit-message.md` | Conventional Commits 提交规范 | 代码提交 |

#### 3.2.2 流程层 (workflow + commands/)

| 命令 | 功能 | 触发方式 |
|------|------|---------|
| `((command:health))` | 环境检查（JDK/Maven/依赖） | 手动调用 |
| `((command:context))` | 显示当前任务上下文 | 手动调用 |
| `((command:status))` | 项目状态总览 | 手动调用 |
| `((command:review))` | 代码审查 | 手动调用 |
| `((command:plan))` | 计划管理（创建/更新/列表） | 手动调用 |
| `((command:knowledge-writeback))` | 知识回写 | 任务完成后 |

#### 3.2.3 执行层 (hooks/)

| 钩子脚本 | 触发时机 | 功能 |
|---------|---------|------|
| `pre-task-start.sh` | 任务开始前 | 检查活跃计划、创建提示 |
| `post-task-complete.sh` | 任务完成后 | 知识回写、计划状态检查 |
| `pre-execute-shell.sh` | Shell 执行前 | 危险命令拦截 |
| `post-execute-shell.sh` | Shell 执行后 | 日志记录 |
| `pre-write-file.sh` | 文件写入前 | 受保护文件确认 |
| `post-read-file.sh` | 文件读取后 | 敏感信息提醒 |
| `post-plan-update.sh` | 计划变更后 | 索引更新、变更日志 |

#### 3.2.4 知识层 (domain/)

| 知识文件 | 内容 | 目标数量 |
|---------|------|---------|
| `glossary.md` | 技术术语表 | ≥100 条 |
| `rules.md` | 业务规则 | ≥50 条 |
| `decisions.md` | 架构/数据/集成决策 | ≥20 条 |
| `state-machines.md` | 状态机定义 | ≥10 个 |
| `edge-cases.md` | 边界情况处理 | ≥30 条 |

### 3.3 计划管理系统

Harness 工程内置完整的计划生成与跟踪系统：

```
workflow-plans/
├── TEMPLATE.md          # 计划模板
├── INDEX.md             # 计划跟踪索引
├── plan.sh              # CLI 管理工具
├── active/              # 活跃计划
│   └── 2026-04-26-feature-xxx.md
├── completed/           # 已完成计划
└── archived/            # 已归档计划
```

**计划状态流转**: `pending → in_progress → completed → [7天后归档]`

**计划命名规范**: `YYYY-MM-DD-{type}-{slug}.md`

## 五、使用指南

### 5.1 日常开发流程

```
1. 任务开始
   ↓
2. AI 自动检查 MEMORY.md 获取项目上下文
   ↓
3. AI 检查相关 rules/ 文件获取编码规范
   ↓
4. AI 检查活跃计划（如有）
   ↓
5. 按 workflow.md 的 7 步流程执行
   ↓
6. 任务完成后执行知识回写
   ↓
7. 更新关联计划状态
```

### 5.2 常用命令速查

| 命令 | 说明 | 使用场景 |
|------|------|---------|
| `((command:health))` | 健康检查 | 环境配置变更后 |
| `((command:context))` | 显示上下文 | 任务开始前 |
| `((command:review))` | 代码审查 | 代码完成后 |
| `((command:plan create))` | 创建计划 | 新任务开始时 |
| `((command:plan update))` | 更新计划 | 任务完成时 |
| `((command:knowledge-writeback))` | 知识回写 | 任务完成后 |

### 5.3 最佳实践

#### 5.3.1 规则编写

- **保持简洁**: 每条规则一句话说明
- **明确触发条件**: 说明何时应用该规则
- **提供示例**: 包含正例和反例
- **定期更新**: 随项目演进持续更新

#### 5.3.2 知识积累

- **及时记录**: 发现新业务知识立即记录
- **结构化存储**: 按模块/领域分类
- **交叉引用**: 规则、术语、决策相互引用
- **定期审查**: 每月审查知识库准确性

#### 5.3.3 计划管理

- **及时创建**: 新任务开始即创建计划
- **状态更新**: 任务完成立即更新状态
- **定期归档**: 完成 7 天后自动归档
- **索引维护**: 保持 INDEX.md 最新

**项目背景**: 医疗业务规则剥离引擎，需要处理复杂的医保结算规则和动态公式计算。

**挑战**:
- 规则引擎开发涉及 Drools、Aviator 等多个技术栈
- 医保业务规则复杂，需要大量领域知识
- 金额计算精度要求极高（BigDecimal 强制使用）
- 安全要求严格（SQL 注入、表达式注入防护）

**Harness 工程应用**:

| 模块 | 应用效果 |
|------|---------|
| 规范层 | 12 个规范文件覆盖所有开发场景 |
| 流程层 | 7 步工作流 + 3 阻塞节点确保质量 |
| 知识层 | 60+ 术语、20 条决策、30+ 边界情况 |
| 计划管理 | 完整跟踪开发进度和状态 |

**成果**:
- ✅ 代码规范遵循率从 60% 提升到 95%
- ✅ 新人上手时间从 3 周缩短到 4 天
- ✅ 安全事故发生率降低 80%
- ✅ 知识复用率从 <20% 提升到 >80%

### 7.2 适用场景扩展

Harness 工程可应用于以下场景：

## 十、结论与建议

### 10.1 结论

Harness 工程体系是一套**成熟、可验证、可扩展**的 AI 辅助开发标准化框架，已在 HIS Drools+Aviator 规则引擎项目中得到成功验证。

**核心价值**:
1. **提升开发效率**: 减少重复工作，规范驱动开发
2. **保证代码质量**: 硬性约束机制，降低人为错误
3. **加速知识传承**: 结构化知识库，新人快速上手
4. **降低安全风险**: Hook 拦截，防止危险操作

### 10.2 建议

#### 立即行动

1. **批准试点计划**: 选择 1-2 个试点项目
2. **分配资源**: 架构师 1-2 人，技术专家 2-3 人
3. **制定时间表**: 8 周推广计划
4. **建立考核**: 设定明确的 KPI 指标

#### 中长期规划

1. **全面推广**: 覆盖所有新项目
2. **集成 CI/CD**: 自动化检查和审计
3. **建立社区**: 内部技术分享和最佳实践
4. **持续优化**: 根据反馈持续改进
