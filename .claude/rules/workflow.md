# 工作流规则 - HIS 动态规则中台

## 触发条件
- 新任务开始
- 任务交接
- 状态同步

## 强制工作流程（7 步，3 个阻塞节点）

> **核心原则**: 确定性 > 建议。每个阻塞节点（★）必须获得用户明确确认方可继续。

```
┌──────────────────────────────────────────────────────────────┐
│ Step 1: 梳理业务逻辑                                          │
│                                                                │
│ 输入: 用户需求描述                                             │
│ 动作:                                                           │
│   ① 读取 MEMORY.md 获取项目事实上下文                           │
│   ② 读取 domain/ 相关文件获取业务知识                            │
│   ③ 阅读 drools_aviator.md / test-jchis-ui-drug.md 了解架构   │
│   ④ 明确需求边界：做什么 / 不做什么                             │
│                                                                │
│ 输出: 业务理解摘要（含已知约束和假设）                          │
│ 进入条件: 无                                                   │
│ 退出条件: 已形成对需求的清晰理解                                │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ Step 2: 规划改动          ★ 阻塞节点 A (必须用户审查)         │
│                                                                │
│ 输入: 业务理解摘要                                             │
│ 动作:                                                           │
│   ① 列出所有涉及的文件（新增/修改/删除 .java / .drl / 公式）    │
│   ② 列出每个文件的具体改动点                                    │
│   ③ 评估风险等级（低/中/高）+ 复杂度预估                       │
│   ④ 定义验收标准（如何判断"做完了"）                           │
│   ⑤ 识别依赖关系和执行顺序                                     │
│                                                                │
│ 输出: 改动计划书                                               │
│ 【⛔ 阻塞】未获用户确认 → 禁止进入 Step 3                      │
│ 进入条件: Step 1 完成                                          │
│ 退出条件: 用户明确批准改动计划                                  │

                           │
                           ▼

│ 动作:                                                           │

│                                                                │
│ 输出: 代码变更集                                               │
│ 进入条件: Step 2 用户已确认                                    │
│ 退出条件: 所有计划的代码变更已完成                              │
└──────────────────────────┬───────────────────────────────────┘
                           │

┌──────────────────────────────────────────────────────────────┐
│ Step 4: 实现审查        ★ 阻塞节点 B (必须用户确认)           │
│                                                                │
│ 输入: 代码变更集 + 原始改动计划                                 │
│ 动作:                                                           │
│   ① 对照改动计划逐项检查是否全部实现                            │

│   ③ 验证 Fact 字段是否全部用 BigDecimal                        │
```

| 任务类型 | 典型示例 | 重点关注的 rules/domain |

## 本项目特有阻塞检查点

Step 4 审查时，除通用检查外，**必须额外确认**：

| # | 检查项 | 原因 |
|---|--------|------|
| C1 | 金额/比例字段是否全部使用 BigDecimal？ | 医保计算不能有浮点误差 |
| C2 | DRL 中是否有硬编码的计算公式？ | 公式应走 Aviator 支持热更新 |
| C3 | 是否使用了 System.out.println？ | 必须用 SLF4J |
| C4 | 公式保存前是否有语法校验和长度限制？ | 防止注入攻击 |
| C5 | Skill 异常是否降级为 WARN 而非向上抛出？ | 保证 Pipeline 不因单个 Skill 崩溃 |
| C6 | 多租户查询是否都带了 tenantId 过滤？ | 数据隔离安全要求 |
